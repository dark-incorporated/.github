# How every Dark Inc. crate is documented

The documentation guidance has three layers, and the higher layer wins: [`STYLE.md`](STYLE.md) at the top, this file in the middle, and a crate's own root `DOCUMENTATION.md` at the bottom.
`STYLE.md` governs names, voice and visuals; this file governs structure and checks; a crate's own `DOCUMENTATION.md` adds that repository's facts and nothing else.

## 1. Who this is for, and the three layers

This guide is for the people and the agents who write a crate's documentation.
"Done" means every measured check passes and the reviewer passes every rubric item: a rule is either **measured**, and names its check (`RC01`–`RC21`, `DC01`–`DC05`, `DR01`, `MC01`–`MC05`, or the rename check), or **reviewed**, and names its rubric item (`RV01`–`RV06`).
No rule is a matter of taste that nobody can check.

The layers work by subtraction, not repetition:

- [`STYLE.md`](STYLE.md) holds the canonical names, the voice and plain words, the palette and the art.
- This file holds the document set, the structure of each document, the checks and the review rubric.
- `<repo>/DOCUMENTATION.md` holds at most 60 lines: a link to both guides, a generated block of repository facts, and two hand-written sections, `## Terms used here` and `## Recorded exceptions`.
  It never restates an org rule, and where it disagrees with them, it is wrong.

## 2. Why these rules

Each rule below either comes from one of these papers or is labelled house style.

- **Prana et al. 2019**, *Categorizing the Content of GitHub README Files* ([10.1007/s10664-018-9660-3](https://doi.org/10.1007/s10664-018-9660-3)): 97% of READMEs say *what* the project is and 88.5% say *how* to use it, but only about a quarter say *why* it exists, and fewer still give its status.
- **Venigalla & Chimalakonda 2022**, *An Empirical Study On Correlation between Readme Content and Project Popularity* ([arXiv 2206.10772](https://arxiv.org/abs/2206.10772)): links correlate most strongly with popularity, followed by lists, images and code; animated images and video show almost no association.
- **Lee 2018**, *Ten simple rules for documenting scientific software* ([10.1371/journal.pcbi.1006561](https://doi.org/10.1371/journal.pcbi.1006561)): treat the README as the only page anyone reads, make the quick start a demonstration plus a copy-paste stub, let examples double as tests, and automate the checks on the docs.
- **Tan, Wagner & Treude 2023**, *Detecting outdated code element references in software repository documentation* ([10.1007/s10664-023-10397-6](https://doi.org/10.1007/s10664-023-10397-6)): 82.3% of the top 1,000 projects had an outdated code reference at some point, and 28.9% have one now, outdated for 4.7 years on average.
- **Chatlatanagulchai et al. 2026**, *Agent READMEs: An Empirical Study of Context Files for Agentic Coding* ([10.1145/3840295](https://doi.org/10.1145/3840295)): developers maintain agent context files like configuration, with a median of about 500 words at H1 to H3 depth.
- **Gloaguen et al. 2026**, *Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?* ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)): context files do not raise task success, they add 20-23% to cost, and files generated by an LLM did worse than none in 5 of 8 settings.
- **Carroll 2014**, *Creating Minimalist Instruction* ([10.14434/ijdl.v5i2.12887](https://doi.org/10.14434/ijdl.v5i2.12887)): start from real tasks, lead with the action, and support error recovery instead of documenting the system.
- **van der Meij et al. 2017**, *Supporting motivation, task performance and retention in video tutorials for software training* ([10.1007/s11423-017-9560-z](https://doi.org/10.1007/s11423-017-9560-z)): a video tutorial works when it is 3 minutes or less, previews, demonstrates, then reviews, and the review step improved retention.
- **van der Meij & van der Meij 2016**, *Demonstration-based training (DBT) in the design of a video tutorial for software training* ([10.1007/s11251-016-9394-9](https://doi.org/10.1007/s11251-016-9394-9)): order tutorials simple to complex, and show the demonstration before asking the reader to reproduce it.
- **Alzahrani 2024**, *Software Systems Documentation: A Systematic Review* ([10.14569/ijacsa.2024.0150816](https://doi.org/10.14569/ijacsa.2024.0150816)): decide the document's purpose and audience first, and version the documentation with the code.
- **LLM-as-judge surveys**, *LLMs-as-Judges: A Comprehensive Survey on LLM-based Evaluation Methods* ([10.48550/arXiv.2412.05579](https://doi.org/10.48550/arXiv.2412.05579)) and *Can We Trust LLM Judges: A Study of Capability-Dependent Biases and Multi-Judge Ensemble for Bias Calibration* ([10.48550/arXiv.2609.12002](https://doi.org/10.48550/arXiv.2609.12002)): judges show position, verbosity and self-preference bias, so the reviewer is another model family, measured checks come first, and a person signs off.

**House style, with no published evidence behind it:** the 250-line README cap, the GIF budgets, and the plain-words rule.
They are here because they keep a family of crates consistent, not because a study measured them.

## 3. The document set of a crate

Every crate carries these documents, and each has one reader in mind.

|Document|Reader|Rule|
|---|---|---|
|`README.md`|someone deciding whether to use the crate|the ordered README, `RC01`–`RC21`|
|`docs/guide/README.md` and one page per task|someone using the crate|guide pages, `RV01`–`RV03`|
|`docs/media/README.md`|whoever recaptures a screenshot|the media manifest, `MC01`–`MC05`|
|`DOCUMENTATION.md` at the repository root|an agent or maintainer working in this repository|`DC01`–`DC05`|
|Rustdoc|someone reading the API|a public item has rustdoc|
|`examples/`|someone who wants a runnable starting point|an example opens the scene its GIF shows|
|one chapter in [the book](https://dark-incorporated.github.io/)|someone reading the whole family|the chapter template, section 10|

`docs/guide/README.md` is an index table with two columns, `| Page | What is in it |`, and one row per page.
A page is one task: "Steer a crowd around walls", not "The `orca` module".

## 4. The repository's own `DOCUMENTATION.md`

The file is made only from the template `.github/templates/REPO_DOCUMENTATION.md` with `tools/repo_doc.py`.
Its generated block, between `<!-- dark-inc:generated:begin -->` and `<!-- dark-inc:generated:end -->`, is never edited by hand: `repo_doc.py` reads the repository's entry in `crates.json` and rewrites the block, and `DC03` fails when the text on disk differs from what the tool renders.

- `DC01`: the file exists at the repository root and is at most 60 lines.
- `DC02`: its first paragraph links both `https://github.com/dark-incorporated/.github/blob/main/DOCUMENTATION.md` and `https://github.com/dark-incorporated/.github/blob/main/STYLE.md`.
- `DC03`: the text between the markers equals `tools/repo_doc.py --repo . --print`.
- `DC04`: the only H2s are `This repository`, `Check it locally`, `Terms used here` and `Recorded exceptions`, in that order.
- `DC05`: every agent file present (`AGENTS.md`, `CLAUDE.md`) contains the exact pointer line in section 13, and no line that links an older documentation guide.

`## Terms used here` defines the terms this repository introduces, one short clause each, at most 8 of them, and stays `None.` when there are none.
`## Recorded exceptions` records a deviation the checks allow but a reader would trip on, as `<rule ID>: <what differs>, because <why>`, and stays `None.` when there are none.
Recorded exceptions are informational: no check reads them, so a crate cannot opt out of a rule by recording one.
A rule that genuinely does not fit is changed in this guide, for every crate.

A new crate joins the family by adding its entry to `crates.json` and running `python3 tools/repo_doc.py --repo <dir>`.
Starting from nothing uses the template repository `dark-incorporated/bevy_crate_template` and `tools/new_crate.py`, which fills every placeholder, renders this file, runs the same checks, and leaves the crate with a passing gate (section 15).

## 5. The README, in this order

1. **Title**: the crate's name. `RC01` the H1 contains the repository name.
2. **The Vibe Coded banner**, the same in every repository and within three lines of the H1 (`RC02`):

   > ⚠️ **Vibe Coded.** Written by AI agents working from a human's direction, covered by tests rather than a line-by-line human review. Read the code before you rely on it for something you care about.

3. **The pitch**: one sentence saying what the crate does and for whom, at most 40 words (`RC03`).
4. **One badge row**: CI, Bevy version and licence badges (`RC04`).
   A published crate, one whose package has a crates.io version, also carries crates.io and docs.rs badges; an unpublished one carries the literal text `git only` and no docs.rs badge.
5. **The hero image**, the first image after the badges: an absolute URL, alt text of at least 5 words, and a one-line italic caption under it (`RC05`, `RC17`).
6. **Status line** (`RC06`): `**Status:** <experimental|usable> · Bevy <x.y>` and, when `Cargo.toml` declares one, ` · MSRV <rust-version>`.
   The level is `experimental` while the root package is below `0.1.0` or unpublished, and `usable` from `0.1.0`; nothing is called `stable` before `1.0`.
   Fewer than a quarter of READMEs say when a project is usable (Prana et al.); this line says it.
7. **Why line** (`RC07`): `**Why:** ` and one sentence on why this crate rather than the obvious alternative, because only about a quarter of READMEs give a why (Prana et al.).
8. **Quick start** (`RC09`): the `cargo add` line, or a git dependency for an unpublished crate, and at most 20 lines of Rust that compile.
9. **Try it** (`RC10`): one `cargo run --example <name>` that opens the hero image's scene.
10. **What you can do** (`RC11`): 3 to 7 top-level bullets of one sentence each, each linking a `docs/guide/` page, with at most 4 inline images.
11. **Part of Dark Inc.** (`RC12`): two sentences linking [the family page](https://github.com/dark-incorporated) and `https://dark-incorporated.github.io/crates/<repo>/`.
12. **Bevy compatibility** (`RC13`): a table of crate versions against Bevy versions.
13. **Learn more** (`RC14`): docs.rs, or the word `unpublished`, then the book chapter, `docs/guide/`, and `CHANGELOG.md`. Links are the README feature that correlates most strongly with popularity (Venigalla & Chimalakonda).
14. **Who and licence** (`RC15`): maintainer `@Ladvien`, the issues link, the org's [`CONTRIBUTING.md`](https://github.com/dark-incorporated/.github/blob/main/CONTRIBUTING.md), and `MIT OR Apache-2.0`.

The H2s appear in that order (`RC08`): `Quick start`, `Try it`, `What you can do`, `Part of Dark Inc.`, `Bevy compatibility`, `Learn more`, `Who and licence`.
At most 2 extra H2s are allowed, and only between `What you can do` and `Part of Dark Inc.`.

Two more rules apply to the whole file:

- `RC18`: besides any GIF, the README carries at least one still image, a screenshot or a diagram.
  Still images correlate with popularity; animated images and video show almost no association (Venigalla & Chimalakonda).
  A crate with nothing to look at uses a scripted diagram still from `art/diagrams.py`, with a caption that says "schematic".
- `RC20`: no forbidden name appears, enforced on `README.md` by `tools/rename.py --check`.
- `RC21`: every README image resolves to a repository file of at most 4 MB, and every GIF is at most 960 px wide.

## 6. Size and moving content

- `RC16`: a README is at most 250 lines.
- Content over the cap moves verbatim to `docs/guide/<slug>.md`, gets a row in the index, and gets a link from the README.
  It is moved, never deleted, and it stays in the repository rather than a wiki, so it is versioned with the code (Lee, rule 6).
  A gallery moves to `docs/guide/gallery.md` with its own index row.

## 7. Guide pages

A guide page follows Carroll and Lee's rule 9: it starts from the task, not from the system.

- `RV01`: the H1 is the task ("Steer a crowd around walls") and the first paragraph says what the reader gets.
- `RV02`: the steps are numbered, each carries a copy-paste command, and they run in the order written.
- `RV03`: an `## If it goes wrong` section names the actual error text and its fix.
- One task per page.
- Identifiers are written in code spans, and every one is a real item (`DR01`): the last segment of each code span must occur as a whole word in some `*.rs` in the repository, apart from package and dependency names and lines of `docs/.doc-refs-allow`.

`DR01` exists because 28.9% of the top 1,000 projects carry an outdated code reference right now, for 4.7 years on average (Tan, Wagner & Treude).

## 8. Walkthroughs

A walkthrough is a book-only page; it teaches a whole job rather than one task, and follows van der Meij et al.

- A preview GIF of the end state opens the page.
- The demonstration is numbered steps, each at most 3 minutes of work, each with a still or a GIF.
- A review recap of 3 bullets closes it.
- Walkthroughs are ordered simple to complex across the book.
- `RV04`: the reviewer checks this structure.

## 9. Media

### GIF and video budgets

`MC03`, measured by `tools/media_check.py`:

- A GIF shows one idea, runs 3 to 8 seconds, loops, is at most 960 px wide, at most 15 fps (every frame lasts at least 66 ms) and at most 4 MB.
- An MP4 (H.264) is for anything over 8 seconds or narrated: at most 120 seconds and 30 MB, with a poster PNG.
- MP4 files are refused in a crate repository: videos live only in [the book](https://github.com/dark-incorporated/dark-incorporated.github.io) (`src/media/`), embedded on the crate's page, and the README links to that page.

Alt text says what happens, and one italic caption line sits under each image or GIF (section 5 of [`STYLE.md`](STYLE.md)).
Media is stored in `docs/media/` and never in Git LFS.

### The media manifest

`docs/media/README.md` lists every image, GIF and video, `MC01`–`MC05`:

- `MC01`: the canonical table is five columns, `| File | Command | Captured | Watches | Shows |`, and every row parses.
  File is backticked, and Captured is `YYYY-MM-DD <sha7+>`.
  Watches is a comma-separated list of globs: the example file plus the `src/` files whose items the example uses.
  Watches is `-` for media that code changes never make stale, such as art copied from `.github/art/`.
- `MC02`: the file exists.
- `MC04`: every image referenced by `README.md` or `docs/guide/**` that resolves into this repository has a row.
- `MC05`, with `--stale`: a row is stale if the Captured sha is not an ancestor of `HEAD`, or if `git log <sha>..HEAD -- <Watches globs>` is not empty.
  `--stale-json OUT` writes the stale rows for the capture phase.
- `MC03`: the GIF budget above.

### Image and link URLs in a README

A README is shown in three places, and they resolve paths differently: GitHub resolves a relative path against the repository; crates.io rewrites a relative path to `https://github.com/<repository>/raw/HEAD/<path>`; **docs.rs rewrites nothing**, so a relative path in a README that rustdoc includes is a broken image there. So, `RC17`:

- Every image in a crate's README is an absolute URL, `https://raw.githubusercontent.com/dark-incorporated/<repo>/main/<path-from-repo-root>`, and every link to a file in the repository is `https://github.com/dark-incorporated/<repo>/blob/main/<path>`.
  Only `#anchor` links may stay relative.
  Pages under `docs/` that only GitHub shows may stay relative.
- **A media file is never moved or renamed once a release has shipped pointing at it.** A published README is frozen on crates.io and docs.rs, so its URLs must keep resolving; if one must move, cut a release with the new URLs the same day.
- The check is an HTTP one: every `<img src>` on the crate's docs.rs and crates.io pages answers 200. `lychee --offline` only checks what stays relative.

### Reproducible media

Captures run on the repository's `capture_host` from `crates.json`: `bmb` for every crate, and `big` for the editor's standing demos, which need a private `Xvfb`.

Frames come from the repository's own capture path: `bevy_devshot`, an example's capture flag, or the editor's demo recorder.
To turn frames into a GIF:

```sh
ffmpeg -framerate 30 -i f_%04d.png -vf "fps=15,scale=960:-1:flags=lanczos,split[a][b];[a]palettegen=stats_mode=diff[p];[b][p]paletteuse=dither=bayer" -loop 0 out.gif
```

## 10. The book

The book lives at [dark-incorporated.github.io](https://github.com/dark-incorporated/dark-incorporated.github.io) and reads `crates.json`, so it has no registry of its own.

- Crate guide pages are synced from the crate repositories by `tools/sync_crates.py` and are never edited in the book; a change is made in the crate and synced again.
- Each chapter's `index.md` follows one template: the header image, the pitch, then `## Add it`, `## What it gives you`, `## Use it in the Dark Factory`, `## Guide` (links to the synced pages) and `## Links`.
- The book's glossary is generated from the canonical names in `names.json`; it is the only place a former name is written.

## 11. README code is tested, in CI

Add this to `src/lib.rs`, unless the crate doc-tests its README some other way, as `bevy_gooey` does in `tests/readme.rs` (`RC19`):

```rust
#[cfg(doctest)]
#[doc = include_str!("../README.md")]
struct ReadmeDoctests;
```

- A block that needs a window is marked `no_run`, never `ignore`.
- CI must run the doctests: `cargo nextest` skips them, so a repository whose CI uses nextest adds a separate `cargo test --doc` step.
- CI builds the examples with `cargo build --examples`; examples double as tests (Lee, rules 2 and 8).

## 12. Docs change in the same PR as the code

A change a user can see updates the README and `docs/` in the same pull request, and a feature is not done until its README line and, if it is visible, its GIF exist.
The mechanical guard is the reusable workflow `dark-incorporated/.github/.github/workflows/readme-check.yml`, which runs this guide's checks against the caller's checkout from `.github@main`, so a rule change in the org applies to every crate on its next CI run with no per-repository edit.

## 13. Agent context files

`AGENTS.md` and `CLAUDE.md` are written by hand and hold commands and rules, not an architecture tour.
Files generated by an LLM did worse than none in 5 of 8 settings, and context files raise an agent's cost by 20-23% (Gloaguen et al.); developers keep them short, like configuration (Chatlatanagulchai et al.).
Agent files are never regenerated, and the only line about documentation in one is this pointer (`DC05`):

> Documentation follows ./DOCUMENTATION.md, which defers to Dark Inc.'s DOCUMENTATION.md and STYLE.md; a feature is not done until its README line and, if it is visible, its GIF exist.

## 14. Review rubric

The reviewer is a model from another family, because judges show position, verbosity and self-preference bias, and it returns a verdict per item.
A run does not land a PR until every item passes and a person signs off.

- `RV01`: the title is task-first, and the lead says what the reader gets.
- `RV02`: the steps are runnable exactly as written.
- `RV03`: `## If it goes wrong` names real errors and real fixes.
- `RV04`: the walkthrough structure of section 8 holds.
- `RV05`: the art rubric of [`STYLE.md`](STYLE.md) section 4 holds, and palette compliance is measured, not judged.
- `RV06`: no claim the code does not support, and every number has a source.

## 15. Regenerating everything

The agent command `/regenerate-docs` runs this whole guide over the family.
It lives at `.omp/commands/regenerate-docs.md` in [the book repository](https://github.com/dark-incorporated/dark-incorporated.github.io) and has four modes:

- `check`: runs every check read-only over every crate in `crates.json` and prints one table of pass and fail counts.
- `run [repo ...]`: makes a worktree per repository, renames the old names, fixes only what the checks measure as stale, recaptures stale media, generates art within a budget, rebuilds the book, has the result reviewed, and writes `REPORT.md`.
- `publish <run-id>`: commits, pushes and opens one pull request per changed repository; it never merges.
- `publish-book <run-id>`: refuses while a run's pull request is unmerged, and otherwise syncs and pushes the book.

Run state lives outside every repository, at `~/.local/state/dark-inc-docs/<run-id>/`, and the report is `~/.local/state/dark-inc-docs/<run-id>/REPORT.md`.
Art is generated only when a job's inputs change, through `art/dark_inc_art.py`, with a cap of $5.00 per run and $0.50 per call.

A brand-new crate uses `tools/new_crate.py` with the template repository `dark-incorporated/bevy_crate_template`; the tool fills every placeholder, renders this repository's `DOCUMENTATION.md`, and runs the same checks before anything is pushed (section 4).
